# Agent-Native 架构设计原则参考

> 整合自两篇外部文章，作为设计指南的理论引用基础。

## 一、Every.to《Agent-Native Architectures》

> - 作者：Dan Shipper & Claude
> - 来源：https://every.to/guides/agent-native
> - 性质：从 Reader、Anecdote 等实际产品提炼的实践指南

### 五原则体系

#### 1. Parity（对等性）

- **定义**：用户通过 UI 能做的一切，Agent 必须能通过工具同等实现
- **为什么重要**：基础原则，没有它其他一切不成立。Agent 只能访问部分功能就无法替代用户完成完整任务
- **示例**：笔记应用中，用户能创建/打标签/搜索/删除笔记，Agent 也必须有对应的工具或工具组合
- **检验方法**：随意选一个 UI 操作，Agent 能完成吗？
- **局限**：某些 UI 交互（拖拽排序、视觉布局）很难映射为工具操作

#### 2. Granularity（原子性）

- **定义**：工具应该是原子化的基本操作，功能由 Agent 在循环中组合原子操作达成
- **为什么重要**：原子工具允许灵活组合。复合工具内嵌决策逻辑会限制灵活性
- **示例**：不要设计 `classify_and_organize_files()`（内嵌分类决策），而是提供 `read_file`、`write_file`、`move_file` 让 Agent 自行决策
- **检验方法**：要改变行为，你是在修改 prompt 还是重构代码？后者说明粒度不够细
- **局限**：过度原子化导致 Agent 需要更多步骤和 token，增加延迟和成本

#### 3. Composability（可组合性）

- **定义**：有了原子工具和对等性，只需编写新 prompt 就能创建新功能
- **为什么重要**：新能力不需要代码变更，用户甚至可以自己修改 prompt 定制行为
- **示例**："周回顾"功能——不写代码实现，而是写 prompt 描述期望结果，Agent 用 `list_files`、`read_file` 等现有工具自行编排
- **约束**：只有在工具足够原子化、能被以未预见方式组合，且 Agent 与用户有对等能力时才成立
- **局限**：依赖 LLM 推理能力，复杂组合可能不稳定

#### 4. Emergent Capability（涌现能力）

- **定义**：Agent 能完成你没有明确设计过的任务
- **为什么重要**：形成反馈闭环——观察用户向 Agent 提什么请求，发现潜在需求
- **示例**："把会议记录和任务列表交叉对比，告诉我哪些已承诺但未排期的事项"——通过工具组合涌现
- **检验方法**：它能处理你领域内的开放式请求吗？
- **局限**：涌现能力不可预测，可能产生错误结果，难以做质量保证

#### 5. Improvement Over Time（持续改进）

- **定义**：Agent-Native 应用通过积累的上下文和 prompt 优化不断变好
- **为什么重要**：改进不需要发版
- **三种机制**：
  - 累积上下文：通过持久化状态文件跨会话保持记忆
  - 开发者级 prompt 优化：部署到所有用户
  - 用户级 prompt 定制：个人工作流个性化
- **高级形态**：自我修改（需安全护栏：审批门、检查点、回滚路径、健康检查）
- **成熟度**：上下文积累和 prompt 优化已验证；自我修改仍在探索

### 关键架构概念

- **文件作为通用接口**：Agent 天然擅长文件系统操作，文件具有可检查性、可移植性、自文档化特性
- **反模式**：
  - Agent 作为路由器（只分发不行动）
  - 先构建再暴露（传统方式开发后再接入 Agent）
  - 请求/响应思维（单次交互而非循环直到完成）
  - 工作流化的工具（把决策逻辑打包进工具）

### 适用场景与局限

- **适用**：小规模数据、重视透明度、云同步完善、移动端优先
- **仍在验证**：文件命名约定、Agent-用户文件冲突、移动端断点续传、审批流的风险/可逆矩阵
- **终极检验**：向 Agent 描述一个你没专门构建功能的结果——它能自行完成吗？能就是 Agent-Native

## 二、Sam Keen《Agent Native Architecture》

> - 来源：https://writing.alteredcraft.com/p/agent-native-architecture
> - 性质：从第一性原理推导的架构理论

### 核心思想：语义优先架构

结构化数据从"推理的输入"变成"推理的输出"。传统设计要求用户适应预定义 schema，Agent-Native 让用户用自然语言表达意图，Agent 在运行时动态生成合适的结构。

### 三个核心要求

1. **LLM 作为推理核心**：Agent 是决策引擎，不是叠加在现有逻辑上的功能层
2. **运行时 Schema 涌现**：使用灵活原语如 `create_item(content, properties)`（Agent 决定属性），而非刚性 `create_task(title, due_date, project)`
3. **全局感知**：Agent 需要持久的用户特定知识：
   - 检索式记忆：语义搜索在相关时找到
   - 构成性知识：始终存在的基础偏好（如"永远不在周五安排会议"）

### 确定性模型

**工具提供硬确定性，Prompt 提供软引导。**

| 位置 | 工具约束 | Prompt 引导 | 特征 |
|------|---------|------------|------|
| 实验型 (A) | 低 | 低 | 最大涌现性，生产风险高 |
| 工具驱动型 (B) | 高 | 低 | 可预测但不灵活 |
| **Prompt 引导型 (C)** | 中 | 高 | **推荐位置**——平衡操作清晰度与领域灵活性 |
| 传统型 (D) | 高 | 高 | 行为完全指定，是否还需要 Agent？ |

### 与传统 Schema-First 的核心差异

| 维度 | 传统 Schema-First | 语义优先 |
|------|-------------------|---------|
| 结构定义者 | 开发者在设计时 | Agent 在运行时 |
| 用户交互方式 | 填写预定义字段 | 自然语言表达意图 |
| 新功能实现 | 开发者编码部署 | 已有工具的新组合 |

### 适用场景与局限

- **适用**：模糊且不断演变的需求、高个性化价值、上下文适当性比精确可复现性更重要
- **不适用**：监管要求确定性可审计行为、错误有严重不可逆后果、需要保证响应时间
- **核心权衡**：用确定性可预测性换取适应性能力

## 三、两篇文章的对比与互补

| 维度 | Every.to（Dan Shipper） | Sam Keen |
|------|------------------------|---------|
| **视角** | 产品/工程实践，从真实产品提炼 | 架构理论，从第一性原理推导 |
| **核心关切** | Agent 如何操作现有应用 | 应用如何为 Agent 重新设计 |
| **入口点** | 对等性——先让 Agent 能做用户能做的事 | 语义优先——先让用户不必适应 schema |
| **工具设计** | 原子工具，从 bash/文件操作起步 | 灵活原语（`create_item(content, properties)`） |
| **确定性** | 隐含在反模式讨论中 | 显式建模为确定性光谱四象限 |
| **共同点** | 涌现能力是核心价值、工具保持原子化、新功能通过组合产生、build-then-expose 是反模式 |

**互补关系**：Every.to 偏"如何改造"（现有产品→Agent-Native），Sam Keen 偏"如何从零设计"。前者提供实践检查清单，后者提供理论坐标系。

## 四、本项目适用性分析

### 可直接引用的结论

1. **Every.to 五原则**可作为设计指南的核心框架，尤其是 Parity、Granularity、Composability 三条
2. **确定性光谱四象限**帮助用户定位自己工具的设计位置（推荐 Prompt 引导型 C 位）
3. **反模式清单**可直接纳入设计指南的"避坑指南"
4. **文件作为通用接口**与 CLI+Skill 方案高度一致

### 需要适配的部分

1. Every.to 框架更偏个人知识管理应用，后续工具可能面向不同领域，需泛化
2. Sam Keen 的语义优先架构适合探索性场景，但后续工具如果有明确输入输出规格，可能更偏工具驱动型 (B)
3. 两篇都承认不适用于高风险/强监管场景，需在设计指南中标注适用边界
